Sovereign AI

Sovereign AI is an AI system whose models, data and controls run on hardware the owner holds, inside a jurisdiction the owner chose. VF Empire builds every system this way: open models on owned metal, EU-only infrastructure, Malta jurisdiction, no third-party AI on a path that touches user data. Cloud capacity is an option when a client wants it, never a requirement, and never where the data has to live.

Used on: Software you own
Local-first

Local-first software keeps your data on your hardware and treats any server as a courier that sees only sealed blobs, never plaintext. It is the first of VF Empire's five principles and every product inherits it: NAV·IT runs full-offline, Guardian Shield scans files on the device, FileIT keeps the books on the owner's machine. The product keeps working when the vendor's cloud does not.

Used on: Software you own
Harness

A harness, in VF Empire's sense, is the frame around an open model that turns it into a worker: process supervision, self-heal loops, project memory and evidence discipline. The harness holds the model, so any open model drops in and inherits the whole system. The Harness Stack page describes the four layers and why a model without one is cargo.

Used on: Harness Stack
Orchestration engine

An orchestration engine routes work across models, gates every output against evidence and self-heals failures. Helmsman is VF Empire's orchestration engine: it installs, tunes and pilots large open models on owned metal, runs the VF floor and ships inside every commissioned system. The model is the part that changes; the router, the gates and the self-heal loops are the parts that stay.

Used on: Helmsman Engine
Command dashboard

A command dashboard is the control surface of an AI system: fleets, lanes, costs and outcomes on one pane of glass. If it runs, it is visible; if it drifts, it pages a person. VF Empire hands every commissioned system over with its dashboards live, and the AI Training Centre teaches dashboard and control design as one of its lanes.

Used on: Command Dashboards
Gate

A gate is the check at the end of every process lane: screenshots, tests, evidence. Nothing ships on a model's word alone. A failed check stops the job where it stands: in FileIT no return leaves without passing evaluation, and in Guardian Shield a detection floor below 85% for 30 days pauses new signups. Humans sit at the gates that matter.

Used on: FileIT
Evidence discipline

Evidence discipline is the rule that every claimed result carries proof: a screenshot, a passing check, a signed response, a registry acknowledgment. It is the fourth layer of the VF harness, and it continues past the product into the security posture, where reproducible builds and a public transparency log let an outsider verify what VF signed and shipped.

Used on: Harness Stack
Self-heal loop

A self-heal loop is the part of the harness that answers failure without a person present. When a model fails, a tool times out or a check is refused, the loop retries, routes around the fault and records what it learned in an improve-queue for the next run. Every one of the 60-plus process lanes on the VF floor runs one.

Used on: Helmsman Engine
Utilisation

Utilisation is VF Empire's research measure: how much real, gated, verified work one model can do per day. The benchmark is finished work, and the levers are batching, routing, tool discipline and context economy inside the harness. The R&D lane on the VF floor tracks harness throughput, self-heal recovery and gated ship rate against it.

Used on: Research and development
Supervised autonomy

Supervised autonomy is a long-running process that keeps running under a watchdog, with memory and an improve-queue, and with humans only at the gates that matter. It is how VF's automated systems and management systems work, and in the robotics lane the same discipline is embodied: perception, planning and self-heal for machines that move.

Used on: Harness Stack
Reproducible build

A reproducible build is a shipping binary that anyone can rebuild byte for byte from the public source. Every VF product binary is reproducible, and third-party CI mirrors in Berlin and Reykjavik build continuously and compare their output against VF's; divergence would be publicly detectable within hours. Reproducibility is what makes a published SBOM checkable.

Used on: Security posture
Transparency log

A transparency log is a public, append-only record of what was signed, when and by whom, kept as an RFC 6962 Merkle tree. VF records every signed update, rule pack and model pack in one, so post-hoc tampering is arithmetically visible and the last signed firmware of any product stays verifiable forever. Anyone can prove an entry is in the log.

Used on: Security posture
Two-operator signing

Two-operator signing, also called 2-of-2 threshold signing, means two operators in separate EU jurisdictions each sign every firmware release, rule pack and signed manifest with a physical Yubikey touch. A 15-minute inspection window sits between signature and publish, and the entry lands in the public transparency log. A single compromised operator cannot ship a malicious release.

Used on: Security posture
Permanence Guarantee

The Permanence Guarantee is VF Empire's written commitment for the day a product ends. If VF discontinues a product, it releases the full source under a permissive open licence within 90 days, the last signed firmware stays verifiable in the transparency log forever, and the sealed vault format stays readable under a public spec. It is a Terms § 15 clause, enforceable in Malta courts.

Used on: Software you own
Cyber Resilience Act (CRA)

The Cyber Resilience Act is the EU regulation for products with digital elements: hardware and software that connects to a network or ships with software the buyer relies on. Enforcement begins on September 11 2026, with fines reaching 2.5% of global turnover. Annex I sets essential requirements, Annex II sets vulnerability handling, and Article 27 requires a technical file. VF audits against all three.

Used on: CRA Readiness Audit
DPIA

A Data Protection Impact Assessment is the document GDPR Article 35 requires before any high-risk processing of personal data. It describes the nature, scope, context and purposes of the processing, analyses the legal basis, and rates each risk by severity and likelihood with its mitigation. VF drafts DPIAs to the shape it publishes for its own products, without softening the ratings.

Used on: Threat Model + DPIA
SBOM

A Software Bill of Materials lists every component inside a shipped release. The Cyber Resilience Act requires one per release, and regulators and downstream buyers expect it signed, in SPDX and CycloneDX formats, with vulnerability scanning attached. A dependency file on its own does not qualify. VF generates an SBOM per build, signed by the same operators who sign the release.

Used on: Signing Infrastructure
ARF (EU digital identity wallet framework)

The Architecture and Reference Framework is the technical rulebook for the EU Digital Identity Wallet under eIDAS 2.0, which requires every EU adult to have access to a wallet by end-2026. It sets the credential model, selective disclosure, presentation protocols and Trust List integration a wallet must conform to. VF Wallet targets full conformance with ARF v1.4, audited by an accredited body.

Used on: VF Wallet
Open model

An open model is an AI model released under an open licence, so the owner can run it on hardware they control, inspect it and replace it. VF Empire builds every system on open models and treats the model as cargo: any open model, today's or next year's, drops into the harness and inherits the whole system. Nothing rented, nothing leaves.

Used on: Helmsman Engine
Build slate

The build slate is VF Empire's numbered list of systems in build, from P·01 to P·24, each with a status: in build, spec complete, in beta or live. Every system on it leaves the lab the VF way: engine fitted, harness tuned, dashboard live, on hardware the owner controls. VF Mail is in beta and SnapIT is live; the rest are moving down the floor behind them.

Used on: All systems

Answered.

What is sovereign AI?

Sovereign AI is an AI system whose models, data and controls run on hardware the owner holds, inside a jurisdiction the owner chose. VF Empire builds every system this way: open models on owned metal, EU-only infrastructure, Malta jurisdiction, no third-party AI on any path that touches user data. The software thesis sets out the five principles behind it.

What is an AI harness?

An AI harness is the frame around an open model that turns it into a worker: process supervision, self-heal loops, project memory and evidence discipline. The harness holds the model, so the model can be swapped and the machine kept. The Harness Stack page walks through the four layers and shows them at work in FileIT, NAV·IT and Guardian Shield.

What is the difference between the orchestration engine and the harness?

The engine moves work; the harness holds the model while the work is done. Helmsman, the orchestration engine, routes each job to a model, gates the output against evidence and self-heals failures. The harness supplies the supervision, memory and evidence discipline each lane runs inside. The command dashboards show an operator both at once.

When a source page changes, the glossary entry changes with it. Facts stay verbatim: dates, statutes, fees and percentages.
